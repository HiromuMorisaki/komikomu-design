# EC API 連携戦略

## 1. 連携順序

| 順 | EC | 採用 API | 理由 |
|---|---|---|---|
| 1 (MVP) | 楽天市場 | 楽天市場商品検索 API（楽天ウェブサービス） | 公式無料・申請ハードル低・ドキュメント豊富 |
| 2 | Yahoo!ショッピング | バリューコマース 経由 or YJDN | バリコマ提携審査あり。楽天実装で抽象化が固まってから |
| 3 | Amazon | PA-API (Product Advertising API) v5 | 売上実績要件（180 日 3 件）あり。楽天/Yahoo で実績を積んでから申請 |

---

## 2. 各 API の要点

### 2.1 楽天市場 商品検索 API

| 項目 | 内容 |
|---|---|
| 申請 | 楽天ウェブサービス（https://webservice.rakuten.co.jp/）でアプリ登録 → アプリ ID 発行 |
| 認証 | アプリ ID（クエリパラメータ） |
| レート制限 | おおむね 1 秒 1 リクエスト（公式の運用目安） |
| 主要エンドポイント | `IchibaItem/Search/20220601`（商品検索）、`itemCode` 指定の個別取得 |
| 取得情報 | 商品名・価格・送料区分・ポイント倍率・JAN コード・商品 URL・画像 |
| アフィリエイト | レスポンスに `affiliateUrl` が含まれる（アプリ ID にアフィリエイト ID を紐付ければ自動付与） |

**実装方針**：

- レート制御は Supabase Edge Function 内で実施（同時実行制限 + バックオフ）
- ユーザーごとではなく **サーバ全体で 1 req/s** に制限する設計
- レスポンスは `price_cache` テーブルに TTL 24h で保存

### 2.2 Yahoo!ショッピング

| 項目 | 内容 |
|---|---|
| API ソース | バリューコマース（https://www.valuecommerce.ne.jp/）経由を採用予定 |
| 認証 | バリコマ提携承認 → API キー発行 |
| アフィリエイト | バリコマの LinkSwitch / SID ベース |
| 注意 | アプリでの利用には **バリコマ側のアプリ事前審査** が必要 |

**実装方針**：

- 楽天と同じ Adapter インターフェースで実装（`_shared/` に Yahoo Adapter を追加）
- 申請から提携承認まで時間がかかる可能性があるため、Phase 1 完了後すぐに申請開始

### 2.3 Amazon PA-API

| 項目 | 内容 |
|---|---|
| 申請 | Amazon アソシエイト承認後 → PA-API 利用申請 |
| 必須条件 | **過去 180 日以内に 3 件以上の適格売上** が必要 |
| 認証 | アクセスキー + シークレットキー（AWS 署名 v4） |
| レート制限 | 売上に応じた TPS（1 売上で 1 TPS、最大 10 TPS） |
| アフィリエイト | アソシエイト ID をリクエストに含める |

**実装方針**：

- 楽天/Yahoo の実績ができてから申請（Phase 2 ～ Phase 3 想定）
- 売上 0 件の段階では PA-API を取得できないため、**MVP では Amazon 連携を入れない**
- 代替案：MVP では「ユーザーが Amazon URL を貼り付けた時、JAN/型番から楽天・Yahoo の同等品を出す」逆向きフローのみ対応

## 3. 同一商品の特定戦略

EC サイト間で商品名・型番が微妙に異なる問題への対応。

### 3.1 マッチングキーの優先順位

1. **JAN コード**（バーコード）：もっとも厳密。楽天 API は `janCode` を返す
2. **メーカー型番**：「Apple AirPods Pro 2 MQD83J/A」のような型番
3. **ASIN**（Amazon 専用）：Amazon URL に含まれる
4. **商品名 + ブランド名 + 主要属性**（容量・色）の文字列類似度

### 3.2 MVP のスコープ

完全な自動マッチングは難しいため、**半自動式** を採用：

1. ユーザーが楽天 URL を貼り付け → 商品情報を取得
2. JAN コードが取れたら → JAN 検索で他モールの候補を取得
3. JAN が取れない場合 → 商品名 + ブランドで他モール検索 → **上位 N 件を候補として表示しユーザーが選択**

### 3.3 Phase 2 以降の発展

- AI による商品名類似度マッチング（OpenAI Embeddings 等）
- ユーザーのマッチング選択を集約して類似商品 DB を構築

## 4. レート制御の集約

複数 EC API のレート制限を統一的に管理：

| 仕組み | 実装場所 |
|---|---|
| トークンバケット | `backend/supabase/functions/_shared/rate-limiter.ts` |
| キャッシュヒット時はスキップ | キャッシュ層と組み合わせ |
| バックオフ | 429 / 503 を受けたら指数バックオフ |

---

## 5. キャッシュ戦略

詳細は [ADR 0004: price-cache-ttl](decisions/0004-price-cache-ttl.md) 参照。

| データ種別 | キャッシュ | TTL |
|---|---|---|
| 商品検索結果（生） | `price_cache` テーブル | 24 時間 |
| 商品価格（個別） | `price_cache` テーブル | 24 時間 |
| 商品マスタ（JAN / 商品名等） | `product_master` テーブル（将来） | 永続 |
| 日次集計値 | `price_history_daily` テーブル | 永続（集計値のみ） |

---

## 6. エラーハンドリング方針

- API エラー時は **キャッシュがあればキャッシュを返し、フロントに「最新取得失敗・◯時間前の値」と明示**
- 全 API がエラーの場合のみエラーをフロントに伝達
- 規約違反となる「他の手段でデータ取得」（例：スクレイピングフォールバック）は **絶対に行わない**（[ADR 0002](decisions/0002-no-scraping.md)）
